## #222 — `location_unresolved` had four derivations, not two

### What the issue said, and what was actually there

The issue named two status mappers that disagree about `partial`. A grep for every write of the
field found two more, both deriving it from **coordinates** rather than from `location_status`:

```
media-query.service.ts        location_status ∈ {pending, no_gps, partial}   → true
media-detail-data.facade.ts   location_status ∈ {pending, no_gps}            → true
media-locations.helpers.ts    !legacyMediaHasGps(display.lat, display.lng)   → coordinate rule
media-detail-view.utils.ts    lat != null && lng != null                     → coordinate rule
```

The third one matters most, because it **overwrites the second**. `locationDisplaySnapshotFromRows`
merges into `media()` on every location rehydrate, so the detail pane's flag was in practice the
coordinate answer, not the status answer. That is TRAP-001 with two questions under one name: "is
this item's location work finished?" and "does the display link have a pin?".

### Why `partial` counts as unresolved

Not a coin flip. `partial` is the D-10 area-only case — an address, no coordinates.
`Archiv/Wien/1010/IMG_0090.jpg` resolves to "Wien 1010" with no street and no pin.

1. The deferred-location backlog shipped 2026-09-21 already counts it as work (`improvable`).
2. `isBulkEligibleStatus` already treats it as work — it has only ever excluded `resolved`/`gps`.
3. The coordinate rule already answered `true` for it, because an address-only display link has no
   coordinates.

So `partial ⇒ unresolved` is the value that lets the two coordinate rules be **deleted without
changing a single observable answer**. Saying `false` would have made the status rule the odd one
out and put a gallery badge in conflict with the backlog badge next to it.

`unresolvable` moved from `false` to `true` for the same reason: terminal for the resolver is not
terminal for the user, and both the backlog and the coordinate rule already called it unresolved.

### Reuse, not a third opinion

`isBulkEligibleStatus` existed precisely to dodge the disagreement, and its doc comment said so. It
now delegates to `isLocationUnresolvedStatus` and the comment says *that* — the comment describing a
disagreement that no longer exists would have been Change-Completeness debt from day one. The
deferred-count query's `located: ['resolved','gps']` literal is now the exported set the predicate
complements, so the query and the classifier are one decision.

### The red that proved something

For a new module the obvious red — write the spec before the module — is TRAP-023: zero tests run.
Written the way [2026-09-20](./2026-09-20.md) records instead: module at its final shape with
`partial` deliberately in the located set, then run. 9 tests, 2 named assertion failures on exactly
the decision (`expected false to be true` at the `partial` line, and again on the gallery load
path). Removing `'partial'` from one array turned it green. The *structural* test — both load paths
agree for every readable status — passed while red, which is the point: sharing one predicate is
what makes them agree, and the rule is a separate question from the sharing.

### Noted, not owned

`MediaRecord.location_unresolved` has **no reader**. Six writers, three pass-throughs, and not one
place that renders or branches on it. That is why the disagreement stayed latent for so long. Filed
rather than acted on — this issue asked for one derivation, not a deletion.
