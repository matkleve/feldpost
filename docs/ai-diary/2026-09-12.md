# 2026-09-12 — Upload pipeline trace harness, and what it found

The user asked to see what actually happens when a batch of files goes through the uploader:
a random batch of ~15 files in differently-named subfolders, then the same thing at 150 files, with
mock data, step by step, including where the Search Object is created and how it gets filled — and
an explicit statement of what is mock and what is real.

## What shipped

A headless trace harness under `apps/web/src/app/core/upload/trace/`, driven by
`scripts/trace-upload-pipeline.mjs` (`npm run trace:upload`). It is a Vitest spec, so it runs the
**real** Angular services — `UploadManagerService`, `classifyBatch`, the token classifier and layer
map, the shipped AT geo assets, the branch gates, content hashing, the queue and phase FSM, all
three pipelines, `persistUploadFile` — against an in-memory Supabase, a 12-row stub gazetteer in
place of Photon, injected EXIF, and synthetic single-byte files. 150 files trace in ~8 s.

Three runs, because the pipeline has three shapes: folder + `required` (address pipeline), flat
multi-file + `optional` (persistence path, which is where the storage key and the `media_items`
insert payload become visible), and folder + `optional`.

Walkthrough and the real-vs-mock table: [`docs/playbooks/upload-pipeline-trace.md`](../playbooks/upload-pipeline-trace.md).
The harness prints the same table itself, because a trace that needs an external legend misleads.

## What it found (no fixes in this change — the pipeline is Sensitive class)

Four of these were not visible by reading the code; they came out of running it.

1. **A camera file name injects a postcode.** `IMG_1274.jpg` under `AT/Wien/1090/Währinger Straße 12/`
   resolves as postcode **1274**. Pass 2 classifies a 4-digit token as a postcode once the country
   is known, and `adminLevelMap` collapse keeps the **lowest** level index — level 0 is the file
   name — so the file name beats the folder. Both rules are as specified;
   `isWeakFilenameStreetLevel` guards the street case and has no numeric counterpart. Consequence:
   `IMG_1274` and `IMG_1275` in one folder get different `groupingKey`s, so two photos of one
   building geocode twice and open two trays.
2. **`Wien` resolves to `Schottwien`.** `at-gemeinden-bev.json` carries `Wien-Alsergrund` … and
   `Schottwien`, but no plain `Wien`. The Fuse match scores `Schottwien` at 0.992, over the 0.98
   write threshold. Every Vienna folder gets `city = Schottwien`, which then disagrees with
   `state = Wien` and opens an `admin_level_conflict` tray for an unambiguous path.
3. **City classification needs an explicit country segment.** The gazetteer is only consulted when
   `country === 'AT'`, so `Graz/Annenstraße 10/DSC_0001.jpg` produces an **empty** Search Object —
   `Graz` becomes a street fragment and `groupingKey` is `|||||`.
4. **Ordinary file names form competing street packages.** `foto.jpg`, `Abnahmeprotokoll.pdf`,
   `Kopie von IMG_1274.jpg` each build a filename layer package that conflicts with the folder
   package and opens a `layer_package` tray.
5. **Volume.** 150 files with plain camera names: **131 tray questions**, 9 automatic placements.
   The same 150 through the persistence path: 144 rows written, 6 duplicates skipped.
6. **`locationRequirementMode: 'optional'` does not skip the address pipeline** on a folder submit.
   The trigger matrix in `upload-address-resolution.phases.md` says it does; in fact `classifyBatch`
   runs regardless and its trays still gate — 13 of 15 files parked in `awaiting_disambiguation`
   before hashing. Only the per-job geocode step reads the mode.

(1), (2) and (6) are spec-level, not implementation slips, so they need a spec decision before a fix.

## Then: database scale

The user's follow-up was the important one — "folders with thousands of files, or tens or hundreds
of thousands, if a company uploads their whole database". That is not the same test, and the
end-to-end harness cannot answer it: measured wall time is 8 s at 150 files, 35 s at 1 000, 72 s at
2 000, ~3.5 min at 5 000.

So `--scale=N` measures the two costs that dominate instead, both against real production code,
streaming paths by index so nothing is materialised:

- **Classification is ~9 ms per file** and it is the fuzzy gazetteer.
  `path-token-classifier.ts:86` builds `new Fuse(items, …)` **per candidate token** and then
  searches 2 114 municipalities with `threshold: 0.4` across two keys. Measured apart: index build
  1.06 ms, search 2.75 ms — so caching the index buys ~30 % and the fuzzy search is the rest. A
  normalized exact-match map consulted before Fuse would remove it for nearly every token.
  This work happens **synchronously inside `classifyBatch`, before the queue drains**, so it is
  time-to-first-byte: ~15 min for 100 000 files, ~2.5 h for a million.
- **The job store is `O(n)` per write, so `O(n²)` per batch.**
  `upload-job-state.service.ts:126` — `_jobs.update((prev) => prev.map(...))` — reallocates the
  whole job array on every field write, and `findJob` at :122 is a linear scan. Measured
  `updateJob`: 0.002 ms at 100 jobs, 0.016 at 1 000, 0.080 at 5 000, **0.573 at 20 000**. At ~15
  writes per job that is 2.9 min for a 20 000-file batch and ~72 min for 100 000. An id-keyed Map
  makes both O(1) and is the highest-leverage change for large batches.
- **Trays do not scale either.** ~45 000 tray questions for 100 000 files. The scale tier runs the
  corpus twice — `camera` naming (`IMG_2001.jpg`) and `neutral` naming (a 6-digit leaf that cannot
  parse as an AT postcode) — and the difference is stark: with camera names **100 %** of groups need
  a question and `branch_a` is **zero**; with neutral names 27 % of the corpus goes straight to
  `branch_a` and the tray share drops to 66 %. Finding (1) above is therefore also the cheapest
  available scale win.

Verdict: a 100 000-file folder is not viable today — roughly 1.5 h of synchronous main-thread work
before uploading is properly under way, plus 45 000 questions. Neither is a network limit.

Two artifacts of my own generator were found and fixed while measuring, and both had distorted a
run: content bodies were a single fill byte cycling every 200 files, so at 5 000 files the corpus
was 82 % accidental duplicates (bodies now carry a per-index seed in their first four bytes); and
the settle budget was a poll count worth 10 s, so a 5 000-file batch reported jobs still mid-flight
(now a 180 s wall-clock deadline, and the count is printed rather than swallowed).

## Left open

  on `main` (type errors in `upload-address-persist.acceptance.spec.ts` and
  `upload-new-pre-resolve-dedup-disambiguation.integration.spec.ts`, inside the gate's recorded
  debt), so `ng test` currently runs **no** specs at all. The gate's note still claims "the test
  bundle now compiles cleanly", which is stale. Run the harness directly with `npx vitest run`
  until that is fixed.
- Branch B (street + project centroid bias) is never exercised, because the harness returns no
  project locations.
