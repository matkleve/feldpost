# 2026-09-11 — P6b (make `job.issueKind` authoritative, UP-07), re-derived on top of PR #129

Continuation of `docs/audits/upload-process-analysis-2026-09-08/11-proposals.md`'s P6b item.
Originally implemented on branch `claude/dazzling-newton-7ihoee` (based on `main` at `9ff30e2`,
2026-09-10), then the user asked to merge that branch directly into `main`. By the time this
session acted on that, `main` had already absorbed a large, independent PR (#129,
`cursor/upload-heic-hash-order-3be6` — a HEIC/hash/dedup-ordering rework that also happened to
land its own `transitionTo`/transition-map mechanism and a **partial** UP-07 fix) merged as
`870963c`. This entry covers discovering that, stopping before merging anything broken, and
re-deriving the fix from scratch against the current `main`.

## What happened

`git checkout -B main origin/main` followed by a trial `git merge --no-commit --no-ff
claude/dazzling-newton-7ihoee` produced **6 conflicting files**, including a literal add/add
conflict where both efforts had independently written `upload-job-state.service.spec.ts` with
different tests for the same failJob-idempotency concern. Investigating instead of resolving
blindly turned up:

- `UploadJobStateService` gained a `transitionTo(jobId, phase, { channel, reason? })` method —
  effectively **P7** ("one phase-write mechanism") already done. `setPhase()` is now a thin
  wrapper (`channel: 'pipeline'`); `failJob()` stayed separate but gained a terminal-phase
  idempotency guard.
- A real `UploadPhase` transition map (`upload-phase-transitions.ts`) with `canTransition()`,
  `TERMINAL_PHASES`/`ACTIVE_PHASES`, and per-channel (`pipeline`/`user`/`system`) rules —
  effectively **P8** already done, under a different audit stream
  (`docs/audits/upload-flow-review-2026-09-10/`, tracked as UP-11 there).
- `getIssueKind()` had already lost the statusLabel string-matching half of UP-07 (the
  `looksLikeDocumentUnresolved`/`looksLikeLocationIssue` regex-ish substring checks), but **kept**
  the phase-based inference fallback (`missing_data` → `missing_gps`, `error` → `upload_error`,
  etc.) — a different, incomplete fix for the same finding.

Reported this to the user with the trial-merge evidence rather than force-resolving six conflicts
in Sensitive-class code by guesswork, and asked how to proceed
(merge-and-hope / resolve-by-hand-favoring-main / stop). Picked: **re-derive the fix on top of
current `main`**, discarding the stale branch's literal diff.

## Re-deriving the fix

Traced every one of the old fallback's phase branches against the **current** code (not assumed
from the earlier session) before touching anything. Good news: almost nothing had moved —
`missing_data`'s producers, the `upload_error` writers in `upload-manager-missing-data.service.ts`,
and the general shape of every function this task touches were structurally identical to what the
2026-09-10 session found, just with `setPhase(jobId, phase)`/`updateJob(jobId, patch)` in some
spots now split into a `transitionTo(jobId, phase, { channel })` call plus a sibling `updateJob`
call carrying the non-phase fields. The exact same gaps were still open:

- `upload-dedup-skip.util.ts`'s `handleDedupSkip` (skipped → missing `issueKind: 'duplicate_file'`)
- `upload-new-prepare-route.util.ts`'s `runConflictCheck` (awaiting_conflict_resolution → missing
  `issueKind: 'conflict_review'`)
- `UploadJobStateService.failJob()` (error → missing `issueKind: 'upload_error'`) — same scope
  question as before (item 6 says never touch `failJob`, but it's the single guarded path for the
  majority of real failures); same resolution as previously agreed: one field added to the patch
  it already builds, signature and every other behavior unchanged.
- `markCancelledSignedOut` (pipeline-host service) and `cancelUploadManagerJob`
  (upload-manager-actions.util.ts) — both `error` writers, both missing `issueKind: 'upload_error'`
- Two "clearer" gaps: `retryUploadManagerJob` and `resolveUploadManagerConflict` never cleared
  `issueKind` on the way back to `queued`
- `upload-location-disambiguation-registration.service.ts` still set
  `issueKind: 'address_ambiguous'` for the paused `awaiting_disambiguation` phase — same fix as
  before: the producer stops setting it (`issueKind: undefined`) rather than keeping a phase-based
  mask in `getIssueKind`, since nothing reads that value except the mask itself.

Re-applied the exact same fix content from the earlier (now-abandoned) branch, adjusted for the
`transitionTo` split: `issueKind` goes on the same `updateJob` call that already carries the
phase's other non-phase fields, not into the `transitionTo` call itself (which stays untouched,
consistent with "don't touch the phase-write mechanism"). Re-extracted the two pure-function
helpers (`buildCancelledSignedOutPatch` in `upload-manager-cancel-active.util.ts`,
`buildAwaitingDisambiguationJobPatch` in `upload-location-disambiguation-registration.helpers.ts`)
for the same testability reasons as before — `markCancelledSignedOut`'s DI weight
(`SupabaseService` + four pipeline services) makes it impractical to unit-test directly.

`getIssueKind()` simplified to `return job.issueKind ?? null;` — deleting the phase-based fallback
this time (the earlier branch's PR only had the statusLabel-matching half still present; the
PR #129 stream had already removed that half, so this session's job was finishing the other half).

Red-test-first: re-wrote 11 tests (one new file for `handleDedupSkip`, extensions to five existing
spec files, and one new describe block layered onto the `upload-job-state.service.spec.ts` PR #129
had already added for terminal idempotency — extended it rather than replacing it, since its
existing tests were unrelated and worth keeping). Confirmed red (9 of 11 failed for the expected
reason; two came back green immediately because PR #129's own `upload-panel.drag-lanes.spec.ts`
had *already* fixed the "routes jobs by matching statusLabel text" test independently — one fewer
thing to invert this time). Then implemented and re-ran green.

Test fallout in `upload-panel`: four pre-existing tests (not five this time — PR #129 had already
fixed the fifth) needed an explicit `issueKind` added to their fixture, for the same reason as the
first pass: they built raw jobs with a phase-shaped `statusLabel` but no `issueKind`, relying on
inference this change removes.

## Mistakes / lessons

- **A `git checkout -B main origin/main` before merging is what surfaced this** — doing the merge
  attempt directly on the feature branch, or worse, force-pushing without first checking how far
  `main` had moved, would have silently produced a mix of two different UP-07 fixes and two
  different phase-write mechanisms in the same file. Always diff/trial-merge before a "just merge
  it" instruction on a branch that's been sitting for more than a few commits, especially in a
  Sensitive-class area with more than one team plausibly working on it concurrently.
- **A stale "known debt" ratchet note in a gate script can look like new debt you introduced.**
  `npm run verify`'s static description strings for `lint`/`test` hadn't been updated since PR #129
  landed, so the live counts (147/1062, 45 failed) didn't match the note (145/1038, 34 failed) even
  with zero problems introduced by this change. The fix was a `git stash` A/B comparison, not
  trusting the note's numbers at face value — and not editing the note myself either, since
  updating it is that PR's/session's job, not this task's.
- **Re-deriving instead of trying to resolve conflicts textually was the right call** — the
  underlying logic gaps turned out to be nearly identical to the first pass (same five sites, same
  fix), so re-typing took a fraction of the time a careful six-file conflict resolution would have,
  with much higher confidence that nothing from the old mechanism (`setPhase`/`updateJob` in one
  call) silently survived alongside the new one (`transitionTo` + `updateJob` split).
