## What we did

**P2b — the upload timeout that never aborts (`0fea55ea`).** The 180s timeout rejected the
`Promise.race` but never touched the underlying `uploadFile()` call, so a late success could
still land a storage object + DB row for a job the UI had already shown as failed. Turned out
worse than the proposal assumed: read the installed `@supabase/storage-js@2.105.4` source
directly and confirmed `.upload()`'s `FileOptions` type has no `signal` field and the runtime
never reads one — the `signal: abortSignal` cast at `upload-file-persist.util.ts:128` has never
done anything. Fix: on timeout, abort the controller anyway (narrows the window for the manual
`abortSignal?.aborted` checks that *do* work) and register a late-arrival cleanup on the
orphaned promise that removes the storage object + row if it resolves after the fact, reusing
the `removeUploadCancelResidue` util from the previous day's P2a.

**P2c — three silent failure paths (`b5a2a9e1`).** A `classifyBatch` rejection could strand a
whole batch at `queued` forever (no caller awaits/catches `submit()`'s returned promise) — fixed
with a guarded helper so `drainQueue()` always runs. The attach pipeline detected an RLS-blocked
write, logged `✗ WRITE DID NOT PERSIST`, and completed the job anyway — `verifyStoragePathWrite`
now returns `{ persisted }` and the caller fails the job instead. The dedup-hash insert ended in
a bare `.then()` (unhandled rejection on failure) — now `.then(undefined, onError)`.

**P5 — repoint every broken spec path (`0196fc9d`).** All ~68 upload-scope broken code-path
references from the audit's `05-spec-drift.md` fixed (17/17 File Map rows in the pipeline spec,
13/15 in the manager spec, the 13-in-13-lines feedback-triage table, a handful more). Archived
`docs/playbooks/upload-manager-playbook.md` (numbers wrong by 40×, phase count wrong, central
advice contradicts a Hard Blocker) with a deprecation header. Wrote specs for the three
previously-unspecced shipped adapters and added the missing `core/upload-resolver-tray-orchestrator`
governance-registry entry. Built `scripts/check-spec-code-paths.mjs`, the CI guard the proposal
asked for — resolves every inline-code path under `docs/specs/**` — wired into `scripts/verify.mjs`
as a `soft` check with the measured non-upload debt (263 broken paths elsewhere in the repo,
out of scope, tracked not fixed).

**P4 — dead code, all six groups (`e68b2536`…`8a3b40a4`).** Deleted: the dead 316-LOC duplicate
panel-dialog service; 7 committed throwaway refactor scripts; the finished-but-incomplete
project-location-tray removal (empty stub, dead facade delegation, test-only helper); 2 dead
files + 5 dead exports + both dead union members (`issueKind:'duplicate_photo'`, `UploadTrayStep
'2'`, collapsed across ~10 read sites and a duplicate type declaration); `USE_TRAY_ORCHESTRATOR`
and its 16 constant-folded guards. `mockResolverTray` (a genuinely live dev/QA affordance
shipping in the production bundle) got the "decide deliberately" treatment the proposal asked

## P6a — stop detecting cancellation by regex (`a836d187`)

UP-08: `isCancelledUploadJob` matched `/cancelled/i` against `job.error` — a plain English
string that goes through i18n. Chose the smaller of the proposal's two offered designs: a
`UploadJob.wasCancelled?: boolean` flag (not a new `cancelled` phase), set at both job-state
cancellation write sites, deliberately avoiding the FSM/`TERMINAL_PHASES`/lane-routing blast
radius a new phase would carry with no transition map to check it against. `isCancelledUploadJob`
now reads the flag. This also fixed Y3 (`03-branch-matrix.md`) as a consequence rather than a
separate change — "cancel modelled as error → UI offers Retry on a cancelled job" —
`retryUploadManagerJob` now refuses a `wasCancelled` job (a real, tested guard) and the panel
menu stops offering Retry for one.

## Mistakes / lessons

- **Assumed "double-encoded" without checking.** Took the audit's characterization at face value
  for the first attempt (one round of windows-1252 reversal), got garbage, checked the actual
  byte chain empirically instead of guessing again, found it needed three rounds. Worth
  remembering: a prior finding's own wording is a lead, not a verified fact, even inside the same
  audit that's otherwise been careful about evidence.
- **A confirmed-working Angular TestBed pattern didn't work for a new spec on
  `UploadPanelItemComponent`.** `fixture.componentRef.setInput('job', …)` before
  `fixture.detectChanges()` is the exact pattern used successfully elsewhere in this repo
  (`media-location-add-search.component.spec.ts`), but threw `NG0950` here regardless of
  ordering, double `detectChanges()` calls, or creating the fixture per-test vs. in `beforeEach`.
  Rather than sink more time or ship a spec with a workaround I didn't understand, dropped the
  component-level test and relied on the fully red-tested service-layer guard
  (`retryUploadManagerJob`) that actually prevents the bug — the component change is presentation
  on top of an already-safe behavior. Left as an open, named question for whoever looks at this
  component's test setup next, rather than silently absent.
- **Console-count and lint-count comparisons need a clean `dist/`.** Cost a false "regression"
  scare on the P4b commit (see above); now always `rm -rf apps/web/dist` before `npm run lint`
  when comparing against a prior measurement.
