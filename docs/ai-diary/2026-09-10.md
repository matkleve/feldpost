## What we did

**P2b — the upload timeout that never aborts (`0fea55ea`).** The 180s timeout rejected the
`Promise.race` but never touched the underlying `uploadFile()` call, so a late success could
still land a storage object + DB row for a job the UI had already shown as failed. Turned out
worse than the proposal assumed: read the installed `@supabase/storage-js@2.105.4` source
directly and confirmed `.upload()`'s `FileOptions` type has no `signal` field and the runtime
never reads one — the `signal: abortSignal` cast at `upload-file-persist.util.ts:128` has never
done anything. Fix: on timeout, abort the controller anyway (narrows the window for the manual
`abortSignal?.aborted` checks that *do* work) and register a late-arrival cleanup on the
orphaned promise that removes the storage object + row if it resolves after the fact, reusing
the `removeUploadCancelResidue` util from the previous day's P2a.

**P2c — three silent failure paths (`b5a2a9e1`).** A `classifyBatch` rejection could strand a
whole batch at `queued` forever (no caller awaits/catches `submit()`'s returned promise) — fixed

write, logged `✗ WRITE DID NOT PERSIST`, and completed the job anyway — `verifyStoragePathWrite`
now returns `{ persisted }` and the caller fails the job instead. The dedup-hash insert ended in
a bare `.then()` (unhandled rejection on failure) — now `.then(undefined, onError)`.

## Adversarial review round — what four reviewers found (PR #129)

Four fresh-context reviewers were run against the branch: behavioral logic, data/contract layer, a geo-mathematics analysis, and a UX analysis. Three of the four found something that changed the outcome. Recording it here because the *method* mattered more than any single finding.

### `CREATE OR REPLACE` does not replace — it overloads (`20260910160000`)

`20260910140000` appended `p_address_precision text DEFAULT NULL` to five functions with `CREATE OR REPLACE`. **Postgres only replaces when the argument list matches exactly**, so each function gained a *second overload* instead. Any call omitting the new argument then matches both candidates and dies with `SQLSTATE 42725` / PostgREST `PGRST203`.

Consequence: `20260910140000` on its own breaks media-detail add-address **and** `markUnresolvable` for every user, independent of anything the frontend sends. `add_media_item_location` breaks *internally*, through its own 13-argument positional call to `find_or_create_location` — so the "just stop sending the parameter from the adapter" fix could never have worked; it swaps `PGRST202` for `PGRST203`.

**This repo already fixed this exact bug once** (`20260525210000_drop_resolve_media_location_nine_arg_overload.sql`), and `scripts/verify-locations-nn-migration.sql` already asserts single signatures. The branch re-broke its own guard. `20260910160000` drops the five stale overloads, extends `add_media_item_location` properly, returns `address_precision` from `list_locations_for_media` + `search_locations` (a written column that could not be read back was dead data), and ends with a `DO` block that raises if any of the eight functions still has more than one signature — necessary because `DROP FUNCTION IF EXISTS` silently no-ops on a signature mismatch.

**How it was found is the point.** The first review was static — it read the same SQL and concluded `CREATE OR REPLACE` made the change *safe* ("no arity gap window"). The second installed PostgreSQL 16 + PostGIS and replayed all 132 migrations, which took the answer from wrong to right and turned up a third broken call the static pass never saw. There is no credential in the agent environment, but that was never the real constraint — a local replay needs none.

### The transition map shipped wrong on eight edges, so it must not have a veto

UP-11's map (`upload-phase-transitions.ts`) was missing the post-dedup edges, because NF-38 moved dedup ahead of location resolution. `setPhase` silently rejected `dedup_check → awaiting_disambiguation` / `→ resolving_location` / `→ conflict_check`, and **every caller ignores the boolean return**, so ambiguous-address tray resolution was functionally dead. A global audit then found six more missing edges. An **eighth** turned up on review: `awaiting_conflict_resolution → queued`, whose `USER_TERMINAL_RESURRECTIONS` entry was unreachable dead code because that phase is not in `TERMINAL_PHASES` — the user channel fell through to the pipeline set, which had no such edge. `resolveUploadManagerConflict` silently failed to requeue and `drainQueue()` ran against a job that was never queued. Conflict resolution had the same break as tray resolution.

The first remedy was to `failJob` on an illegal transition, on the reasoning that a silent stall is invisible. **That was worse, in a checkable way.** Since call sites run on regardless, a missing edge previously meant a wrong *label* on a job that still finished. With `failJob`, `upload-replace-pipeline-finish.util.ts:168` would store the file, save the record, call `markDone` — then show "Upload failed" and invite the user to re-upload something already stored. Failing in the destructive direction, on the authority of a map wrong eight times.

Final design: **terminality is the only hard invariant.** Every other edge is an *assertion about pipeline structure*, not a permission. An unmapped non-terminal transition reports (Vitest hook throws, `ngDevMode` logs) and then **applies**. When map and pipeline disagree, the pipeline is the authority and the map is the bug. Recorded in `upload-manager.phase-fsm.supplement.md` § Guard policy.

## Mistakes / lessons

- **A static read of SQL is not verification.** "No credentials, therefore static only" was accepted once and produced a confidently wrong answer on the load-bearing claim. Installing Postgres and replaying the migration chain costs minutes and needs no credentials. Treat migration review without a replay as unreviewed.
- **Fourth instance of *a condition that doesn't say what it means*.** `!isHeic(job.file)` for "prepare finished"; `resolving_address` labelling an empty function; `locationPinEligible` for precision — and now **`CREATE OR REPLACE` reading as "replace"**. Every one was legible to a reader and wrong. This is the repo's most expensive recurring shape and it has no home; `docs/TRAPS.md` does not exist (audit item D4's fourth memory, still unbuilt).
- **A guard is only as trustworthy as the map behind it.** The instinct on finding a silent rejection was to make it loud *and fatal*. Loud was right; fatal inverted the failure into the destructive direction. Ask what happens when the guard itself is wrong before giving it authority over user work.
- **Piping a batch creation script through `head` truncates the process, not the output.** `create-github-issues.mjs … | head -6` killed the run after six creations, producing duplicate issues #130–#135. Never pipe a write-side script through a pager or `head`.
- **The agent token can create issues but not update them** (`403 Resource not accessible by integration` on any edit, including comments). Plan issue batches to be correct on first write; there is no cleanup path from inside an agent.
- **Anchor mismatches make geometry numbers look wrong when they are not.** A reviewer flagged the geo analysis's ~19.7 km Vienna figure against an 18.6 km half-diagonal. Both are right: 18.6 km is centre-anchored, and the geocoder's returned point sits ~1.4 km off centre, so the farthest corner is 19.9–20.0 km. The equal-area disc is centred on that same point, so like-for-like is 19.9 vs 14.6 km. State the anchor whenever quoting a radius.

## The database is not paused — it is starved

Postgres logs exported from the dashboard for 20:39–21:08 settle what "Database not usable /
CONNECT_TIMEOUT" was. A paused project emits no logs at all, so logs existing at all proves the
instance is up. What the logs show instead is that **Supabase's own telemetry queries are taking
eleven seconds**:

- `SELECT SUM(size)/(1024*1024) FROM pg_ls_waldir();` — 11,719 ms. This is a directory listing of
  `pg_wal`. It has no business taking longer than milliseconds.
- The platform's `pg_stat_statements` "user queries total" aggregate — 11,255 ms.

Neither is ours, and neither is expensive. When the queries the *platform* runs to measure the
database are that slow, the bottleneck is the instance (IO or CPU), not a statement. Everything
else in the export is downstream of that one fact: repeated `57014 canceling statement due to
statement timeout`, `08006 could not receive data from client: Connection reset by peer` (clients
giving up), and the TCP-layer `CONNECT_TIMEOUT` the lint reported.

Two things the logs do **not** contain, both worth stating because their absence is evidence: no
statement text on the timed-out queries, so the saturating workload cannot be named from here; and
no application or migration traffic, so nothing points at the upload migrations or app code.

A second export, from the Storage service, confirms it from a third vantage point and rules out
"one bad client". Supabase's management API polls `GET /tenants/<ref>/health`, and that health
check queries the database. 7 of 33 polls came back `ABORTED REQ` — the caller gave up — while the
neighbouring `GET /tenants/<ref>` (tenant config, no database access) returned 200 every time. The
service that touches the database fails; the one that does not, succeeds.

The diagnostic order, cheapest first: **disk usage** (a full disk fits every symptom here,
including a slow `pg_ls_waldir()`, and is the one cause whose remedy is "resize", not "wait"),
then Reports → Database for memory, CPU, and **disk IO burst balance** (a depleted burst balance on
a small instance produces exactly this cliff, where even trivial queries go to seconds), then a
project restart to clear a wedged backend or an `idle in transaction` session — but only after
checking disk, because a restart on a full disk does not come back clean.

What is *not* available during this: the dashboard SQL editor also fails with `Connection
terminated due to connection timeout`, so `pg_replication_slots` and `pg_stat_activity` cannot be
read. **Any diagnosis that requires a database connection is unavailable exactly when it is
needed.** Everything above deliberately reads from platform metrics instead.

**Trap:** "the DB is unreachable" reads as "the project is paused", and both produce a connect
timeout at the client. The logs distinguish them for free. Check for the presence of logs before
theorising about the cause of their absence.

1. Probed `check_dedup_hashes` with parameter `p_content_hashes`. `PGRST202`. The real parameter is

2. Probed `find_photoless_conflicts` with `p_media_type`. `PGRST202` again. Third parameter is

Only the third attempt was decisive: `find_photoless_conflicts(p_lat, p_lng, p_address)` has the

and returns 200 to an anonymous caller. So PostgREST does not hide those functions from `anon`,
and `retire_dedup_hashes_for_media_item`'s `PGRST202` means genuinely absent rather than merely
invisible. **A negative result is only evidence once a positive control with the same shape
succeeds** — otherwise you are measuring your own request, not the server.

### `REVOKE ALL ON FUNCTION … FROM PUBLIC` does not block `anon`

Falling out of that control is a real finding, filed as issue #193. Supabase ships
`ALTER DEFAULT PRIVILEGES … GRANT ALL ON FUNCTIONS TO anon`, so `anon` gets its **own** grant at
`CREATE FUNCTION` time. `REVOKE … FROM PUBLIC` strips only the implicit `PUBLIC` grant and leaves
that one intact. Demonstrated: an unauthenticated call, JWT payload `{"role": "anon"}`, executed a
`SECURITY DEFINER` function the migration author had gated to `authenticated`.

No data leaks today, because these functions are org-scoped through `public.user_org_id()`, which
returns `null` for `anon` — verified in the same run. That is defence in depth doing its job. But
the outer layer is decorative, and the next `SECURITY DEFINER` function that omits the org
predicate has no second line.

Not promoted to TRAPS: by the promotion rule there it has bitten once with **no** user-visible
consequence. Recording it here as a candidate is the correct weight, and TRAPS keeps its value by
not accepting everything interesting.
