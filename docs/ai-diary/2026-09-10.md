## What we did

**P2b — the upload timeout that never aborts (`0fea55ea`).** The 180s timeout rejected the
`Promise.race` but never touched the underlying `uploadFile()` call, so a late success could
still land a storage object + DB row for a job the UI had already shown as failed. Turned out
worse than the proposal assumed: read the installed `@supabase/storage-js@2.105.4` source
directly and confirmed `.upload()`'s `FileOptions` type has no `signal` field and the runtime
never reads one — the `signal: abortSignal` cast at `upload-file-persist.util.ts:128` has never
done anything. Fix: on timeout, abort the controller anyway (narrows the window for the manual
`abortSignal?.aborted` checks that *do* work) and register a late-arrival cleanup on the
orphaned promise that removes the storage object + row if it resolves after the fact, reusing
the `removeUploadCancelResidue` util from the previous day's P2a.

**P2c — three silent failure paths (`b5a2a9e1`).** A `classifyBatch` rejection could strand a
whole batch at `queued` forever (no caller awaits/catches `submit()`'s returned promise) — fixed
with a guarded helper so `drainQueue()` always runs. The attach pipeline detected an RLS-blocked
write, logged `✗ WRITE DID NOT PERSIST`, and completed the job anyway — `verifyStoragePathWrite`
now returns `{ persisted }` and the caller fails the job instead. The dedup-hash insert ended in
a bare `.then()` (unhandled rejection on failure) — now `.then(undefined, onError)`.

**P5 — repoint every broken spec path (`0196fc9d`).** All ~68 upload-scope broken code-path
references from the audit's `05-spec-drift.md` fixed (17/17 File Map rows in the pipeline spec,
13/15 in the manager spec, the 13-in-13-lines feedback-triage table, a handful more). Archived
`docs/playbooks/upload-manager-playbook.md` (numbers wrong by 40×, phase count wrong, central

previously-unspecced shipped adapters and added the missing `core/upload-resolver-tray-orchestrator`

  needed — but it's worth flagging in this diary precisely because it's new to this codebase, so
  the next reader doesn't have to rediscover why four tests in this commit look unusual.

- **`awaiting_disambiguation`** — the old `getIssueKind` had a phase check *above* the

  overwriting whatever was there). So instead of keeping a phase-based mask in `getIssueKind`
  (which the task explicitly wants gone — "a simple `return job.issueKind`"), the producer
  itself no longer sets it: `issueKind: undefined` at the point the job is parked, same
  observable behavior, no special case needed downstream.

### The one real scope conflict — `failJob()`

The task's own instructions were self-contradictory on the `error` phase: item 1 says trace
through "error phase writers," item 6 says never touch `setPhase`, `failJob`, or direct `phase:`
writes. `failJob()` is the single guarded path essentially all real upload failures go through
(validation errors, storage errors, etc.) — skipping it silently would have left the *majority*
of genuine failures with no `issueKind` at all post-fix, i.e. dropped out of the Issues lane
entirely (no Retry action, wrong lane count) the moment the fallback was deleted. Asked the user
rather than guess on a Sensitive-class change with that much blast radius; picked option
"add the one field inside `failJob()`'s own patch, signature and all other behavior unchanged" —
read "do not touch failJob" as "do not restructure/unify it" (that's P7's job), not as
forbidding a one-line, unconditional addition to the object literal it already builds.
`setPhase()` stayed genuinely untouched (it is used by ~15 phase transitions that have nothing
to do with issues, so it can't safely gain an `issueKind` param) — its one issue-adjacent call
site (`runConflictCheck`'s `awaiting_conflict_resolution` write) instead got `issueKind` added to
the sibling `updateJob()` patch that already ran right next to it, not inside `setPhase` itself.

### Correction to this file's own earlier "Next" note

The `## Next` section above (written at the end of the morning session) said P6b "would directly
resolve T16." It doesn't. T16/UP-24 is a *different* bug — `routeJobToMissingData` and
`finalizeNewUploadPhase`'s failed-geocode routing use two different document-vs-photo
classifiers (`resolveMediaType()` with an extension fallback vs. raw `job.file.type`) and can
disagree on which `issueKind` to assign for the same file. Both already set `issueKind`
explicitly before this task started, so making `getIssueKind()` authoritative doesn't touch
which value either one computes — confirmed by running that spec after this change and seeing
it still fail the same way. UP-24 needs its own fix (pick one classifier, or share it) and stays
open.

### Mistakes / lessons

- **A proposal's scope estimate ("sweep of 5 writers") can already be stale by the time you
  start** — checking `git log`/current code before assuming a described gap still exists saved
  writing five no-op fixes and five redundant tests here. Worth doing before any "fix N sites"
  task, not just this one.
- **An explicit "do not touch X" instruction can conflict with the task's own correctness
  requirement.** When it does on Sensitive-class work, asking the user with a concrete preview of
  each option (rather than picking the least-risky-looking reading and hoping) is worth the
  round trip — the three real options here (touch `failJob`'s own patch, accept a real lane
  regression, or fan a companion call out across ~15 call sites) had meaningfully different risk
  profiles and the "obviously right" one wasn't obvious from the instruction text alone.
- **A test that asserts the exact behavior a task is fixing is a real regression signal, not
  noise to silence.** `'routes jobs with missing-location status text to issues lane'` failing
  was the correct outcome — the fix was to invert the assertion, not add the missing `issueKind`
  to make the old (wrong) assertion pass again.
